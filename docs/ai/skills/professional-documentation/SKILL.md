# Professional Documentation

## Objetivo

Garantir que a documentação é conceptual, sénior e apresentável — adequada para equipas técnicas, recrutadores, clientes ou futuros maintainers.

## Princípios

### Clareza Técnica

- Explicar o quê e porquê, não apenas o quê
- Usar linguagem técnica precisa
- Fornecer contexto arquitetural
- Incluir exemplos quando útil

### Profundidade Adequada

- Nível sénior, não básico
- Assumir conhecimento técnico do leitor
- Focar em decisões e trade-offs
- Documentar o não óbvio

### Apresentabilidade

- Estrutura clara com títulos e índice
- Formatação consistente
- Código formatado corretamente
- Sem jargão desnecessário

## Checklist

### Para README

- [ ] Título claro e descritivo
- [ ] Descrição do que o projeto faz
- [ ] Quick start funcional
- [ ] Requisitos listados
- [ ] Instalação documentada
- [ ] Uso com exemplos
- [ ] Configuração explicada
- [ ] Contribuição guidelines (se aplicável)
- [ ] Licença clara

### Para Documentação de Arquitetura

- [ ] Visão geral do sistema
- [ ] Diagrama de componentes (texto ou link)
- [ ] Responsabilidades de cada módulo
- [ ] Fronteiras e interfaces
- [ ] Fluxos de dados
- [ ] Decisões técnicas documentadas
- [ ] Trade-offs explicados

### Para Documentação de API

- [ ] Endpoints documentados
- [ ] Request/response examples
- [ ] Códigos de erro
- [ ] Autenticação explicada
- [ ] Rate limits (se aplicável)

## Erros Comuns

| Erro | Correção |
|---|---|
| "Isto faz X" | "Este módulo implementa X para Y" |
| Apenas código | Código + explicação + contexto |
| Sem exemplos | Incluir exemplos funcionais |
| Desatualizado | Manter atualizado com código |
| Inconsistente | Usar mesma estrutura em todos os docs |

## Processo

1. Identificar público-alvo
2. Definir objetivos do documento
3. Estruturar com títulos claros
4. Escrever conteúdo técnico
5. Revisar para clareza
6. Verificar consistência
